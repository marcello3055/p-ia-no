# Áudio de candidatos — 4.9

Treinamento → histórico → geração → detalhes do candidato → Preparar áudio de piano. Após preparo, player nativo e download MP3. Renderização ocorre no servidor; não inicia treinamento. Reproduzir um áudio pausa os demais. Trocar geração/sessão desmonta players, cancela requisição do cliente e libera URLs temporárias. A renderização já iniciada no servidor termina para liberar recursos com segurança.

POST /api/sessions/{session}/generations/{generation}/candidates/{id}/audio retorna audio/mpeg. Antes de renderizar, recupera o MIDI com as verificações de fonte, código, cadeia e hash do bloco 4.8. Passa esse MIDI diretamente a render_piano, sem nova redução baseline. Verifica hash da entrada informado pelo renderizador e hash do MP3. Cabeçalho X-Piano-Midi-SHA256 identifica entrada verificada. MIDI permanece interno; resultado audível é piano solo.

Lock por aplicação/processo recusa requisição concorrente com 503; worker mantém lock durante execução. Limite herdado de 120 segundos. Cache em memória por MIDI + SoundFont, até 8 áudios/24 MiB; mesmo em cache a origem é revalidada. Reiniciar processo limpa cache. Alterar código/renderizador/dependências exige reiniciar servidor. Cache não é backup ou armazenamento definitivo e não é compartilhado entre processos. A rota experimental antiga usa lock próprio: produção ainda exige fila unificada. Sem GPU, dependência ou serviço pago novo.

Fonte: source.mid na pasta da sessão. Restaurações do bloco 4.5 incluem esse arquivo; sessões anteriores sem fonte precisam de recuperação pelo agente. Retorna 404 para candidato inexistente, 409 para proposta incompatível/limite, 503 para recurso indisponível. Não renderiza automaticamente todos os candidatos. Arquivos temporários WAV/MP3 são removidos após leitura; navegador permite baixar o MP3 enquanto o componente estiver aberto.
